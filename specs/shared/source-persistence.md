# 소스 저장소의 Spring Data JPA 전환

소스와 첨부 메타데이터를 Spring Data JPA 저장소로 접근한다. 운영 스키마와 API 계약은 소스 명칭 전환에 사용한 정의를 따른다. 스키마 초기화와 기존 데이터 이관은 SQL 스크립트가 담당한다. Hibernate의 스키마 검증은 매핑 오류를 초기화 단계에서 드러낸다.

- 소스 등록은 JPA의 IDENTITY 매핑으로 DB가 발급한 식별자를 즉시 받는다. 소스 상세값은 PostgreSQL `details jsonb` 열에 보관한다. 목록은 [저장된 공통 이름](source-name.md)과 유형별 요약을 읽고 [허용된 정렬 속성](source-pagination.md)을 JPA 페이지 조회에 적용한다. 정렬을 생략하면 등록 시각과 식별자 내림차순을 사용한다.
- 소스 수정·삭제는 기존과 같은 행 잠금으로 직렬화한다. 업로드 예약은 `ON CONFLICT DO NOTHING`으로 멱등성을 유지한다. 일반 업로드와 복구는 각각 `FOR UPDATE`, `FOR UPDATE SKIP LOCKED` 고정 쿼리를 사용한다.
- 첨부 삭제는 PostgreSQL `DELETE ... RETURNING`이 반환한 객체 키를 JPA 커스텀 저장소에서 읽는다. Spring Data의 `@Modifying` 메서드는 영향 행 수나 반환값 없는 실행을 위한 방식이므로, 동일 SQL 문에서 삭제와 키 반환을 유지하려면 결과를 읽는 실행 경로가 필요하다.
- 서비스에서 선언한 트랜잭션 경계, 소스 상세 읽기의 반복 가능 읽기 격리, 업로드 예약의 독립 커밋, 원본 삭제 이벤트의 커밋 후 실행을 유지한다. Spring의 Hibernate 트랜잭션 관리자가 상세 조회에 격리 수준을 적용하도록 연결 해제 시점을 JPA 세션 종료로 설정한다. 정리 작업은 하나의 SQL 문에서 저장 및 미완료 예약 키를 함께 조회한다.

검증은 Java 21에서 기존 HTTP, 동시 요청, 롤백, 정리 테스트를 실행하고 별도 PostgreSQL 검증 스키마에서 결과를 확인한다. 소스 저장 후 조회와 첨부 삭제가 반환하는 키를 검증하며, SQL 실패 시 기존 메타데이터가 유지되는지 확인한다.
