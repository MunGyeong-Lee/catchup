## 1.0 적용 범위

이 문서는 캐쳡 백엔드에 적용할 공통 응답 규칙을 정의한다. 소스 등록, 소스 목록 조회, 첨부 목록 조회 및 이후 로그인 기능에서 구조화된 응답 형식을 통일한다. 첨부 파일 다시 열기와 원본 내려받기의 성공 응답은 원본 바이트와 콘텐츠 헤더를 유지한다. 파일 전송이 시작되기 전에 발생한 오류는 공통 오류 형식을 사용한다.

<a name="section-2-0"></a>

## 2.0 공통 응답 형식

공통 응답 객체는 `ResponseVo`다. 정상 응답은 `ResponseVo.buildResponse(data)`로 생성한다. 반환할 데이터가 없는 성공 응답은 `ResponseVo.buildResponse()`로 생성하고 `response`를 `null`로 설정한다.

| 필드 | 정상 응답 | 오류 응답 |
| --- | --- | --- |
| `error` | `null` | 프론트엔드가 동작을 결정할 수 있는 고정 오류 코드 |
| `error_message` | `null` | 사용자에게 표시할 수 있는 오류 설명 |
| `response` | 기능별 응답 데이터 | `null` |

응답 본문과 함께 실제 처리 결과에 해당하는 HTTP 상태를 사용한다. 조회 성공은 `200`이고 등록 성공은 `201`이다. 오류 설명에는 내부 예외 문자열, 저장소 키, 자격 증명을 포함하지 않는다.

<a name="section-2-1"></a>

### 2.1 정상 응답

소스 등록 성공의 상태는 `201 Created`다. 소스 목록의 상태는 `200 OK`이며 `response`는 [페이지 객체](source-pagination.md)다. 소스가 없으면 `response.items`가 빈 배열이다.

```json
{
  "error": null,
  "error_message": null,
  "response": {
    "sourceId": 1
  }
}
```

<a name="section-2-2"></a>

### 2.2 오류 응답

소스 검증 실패의 상태는 `400 Bad Request`다. 입력 검증 실패에만 `field_errors`를 추가한다. `field_errors`에는 입력 항목 이름과 사용자에게 표시할 오류 메시지를 담는다. 정상 응답과 입력 검증 이외의 오류 응답에서는 이 필드를 생략한다.

소스 상세 입력 검증은 첫 실패의 필드와 메시지 한 건을 반환한다. 등록과 수정에서 요청 객체의 키 순서와 관계없이 다음 순서를 적용한다.

1. 소스 유형 `sourceType`, [공통 이름 `name`](source-name.md), 유형별 입력을 차례로 확인한다. 수정 요청에서는 유형별 입력을 담는 `details` 객체도 확인한다.
2. 해당 유형에 정의되지 않은 필드가 있으면 `details` 오류를 반환한다.
3. 입력한 필드의 값 형식을 필드 이름 오름차순으로 확인하면서 문자열의 앞뒤 공백을 제거한다. 빈 문자열과 `null`은 생략한다.
4. 필수 항목의 누락을 소스 유형에 선언된 순서대로 확인한다.
5. 이력 구분, 시작 날짜 또는 연월의 형식, 종료 날짜 또는 연월의 형식, 기간의 순서, 진행 중 이력의 종료 연월 금지, 링크 형식 순서로 해당 유형에 적용되는 규칙을 확인한다.

검증은 여러 오류를 담은 동일 요청에서 키를 재배열해도 동일한 HTTP 400 응답과 단일 `field_errors` 항목을 반환하는지 확인한다. 정상 입력은 기존과 같이 정규화해 저장 흐름에 전달한다.

```json
{
  "error": "VALIDATION_FAILED",
  "error_message": "입력한 내용을 확인해 주세요.",
  "response": null,
  "field_errors": {
    "title": "필수 입력 항목입니다."
  }
}
```

## 3.0 오류 코드와 예외 처리

| 초기 오류 코드 제안 | 응답 상태 | 사용 상황 |
| --- | --- | --- |
| `INVALID_REQUEST` | `400` | 읽을 수 없는 요청 본문 또는 잘못된 식별자 형식 |
| `VALIDATION_FAILED` | `400` | 소스 입력값 또는 첨부 파일 형식 검증 실패 |
| `ATTACHMENT_NOT_FOUND` | `404` | 요청한 소스에서 첨부 파일을 찾을 수 없음 |
| `PAYLOAD_TOO_LARGE` | `413` | 첨부 파일이나 요청 크기 제한 초과 |
| `INVALID_RANGE` | `416` | 첨부 파일의 바이트 범위 오류 |
| `ATTACHMENT_STORAGE_UNAVAILABLE` | `503` | 첨부 원본 저장소 장애 |
| `INTERNAL_ERROR` | `500` | 분류하지 못한 서버 오류 |

- `ErrorCode` 열거형에 코드와 기본 사용자 메시지, 응답 상태의 대응을 정의한다.
- 서비스는 업무 오류를 표현하고, 복구가 필요한 경우 실제 복구 흐름을 실행한다. 복구 후 남는 오류를 컨트롤러 경계로 전달한다.
- `@RestControllerAdvice`를 사용하는 전역 예외 처리 클래스가 업무 예외와 요청 파싱 오류를 공통 응답으로 변환한다. 처리 가능한 오류를 컨트롤러마다 반복해서 잡지 않는다. 예상 밖의 오류는 서버에 기록하고 사용자에게 일반 오류 메시지를 반환한다.
- 응답 스트리밍이 시작된 뒤 전송이 끊긴 경우에는 최초 응답을 공통 오류 본문으로 바꿀 수 없다. 스트리밍 실패는 서버에 기록한다.

<a name="section-4-0"></a>

## 4.0 적용 및 검증 순서

1. [소스 등록 이슈](../issues/01-source-create.md)와 [소스 목록 페이지 계약](source-pagination.md)을 확인한다.
2. 정상 응답, 빈 목록, 항목별 입력 오류, 크기 초과, 저장소 장애, 파일 원본 응답의 기대 형식을 테스트로 정의한다.
3. 공통 응답 객체와 전역 예외 처리를 구현하고, 백엔드 응답과 프론트엔드 응답 읽기를 함께 전환한다.
4. 등록 오류가 입력 항목에 표시되는지, 빈 목록이 정상적으로 표시되는지, 첨부 열기와 내려받기가 정상 동작하는지 확인한다.
5. 새 기능 명세서는 공통 응답 설계를 링크하고 기능 고유의 응답 데이터와 오류만 정의한다.

<a name="section-5-0"></a>

## 5.0 미결정 사항

- 현재 합의가 필요한 사항은 없다.
